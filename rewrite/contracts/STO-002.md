# STO-002 Contract: Bounded Chunks And Reusable Workspace

## Responsibility

STO-002 converts a byte budget into a reusable canonical payload capacity and
plans deterministic level-1 block chunks over STO-001 and TOP-001. It defines
no file format, source class, halo values, operator state, transaction, or hard
OS resident-set limit.

## Managed Workspace Budget

For slot capacity `S`, selected field count `F`, and spatial workspace shape
`(sx, sy, sz)` with volume `V`, the managed arrays are:

```text
payload   float64[S,F,sx,sy,sz] = 8*S*F*V bytes
block_ids int64[S]              = 8*S bytes
managed bytes                   = 8*S*(F*V + 1).
```

`workspace_nbytes(...)` returns this exact integer. Given nonnegative
`budget_bytes` and `block_count`, `workspace_slot_capacity(...)` returns

```text
min(block_count, floor(budget_bytes / (8*(F*V + 1)))).
```

`field_count` and spatial extents are positive. `budget_bytes`, `block_count`,
and `slot_capacity` are nonnegative.
All products must be representable as signed `int64`; invalid values or
overflow are rejected. The budget covers full allocated capacity, including
unused final-chunk slots. NumPy object headers, borrowed topology/source arrays,
consumer outputs, virtual mappings, and OS page cache are outside this explicitly
managed byte count and must be reported separately when relevant.

## Chunk Planning

```text
plan_level1_chunk(
    first_primary_id,
    face_neighbor_ids,
    include_face_closure,
    chunk_block_ids,
) -> (primary_count, selected_count)
```

- `face_neighbor_ids` is a borrowed read-only TOP-001 `int64[N,6]` table.
- `chunk_block_ids` is caller-owned writable C-contiguous `int64[S]`, where `S`
  is the reusable payload slot capacity.
- `first_primary_id` is in `[0,N]`; value `N` returns `(0,0)` without mutation.
- `include_face_closure` is a Python bool.

Primaries are the maximal nonempty ascending contiguous interval
`[first_primary_id, first_primary_id + primary_count)` that fits capacity.
They occupy `chunk_block_ids[:primary_count]` in ascending order, so consumer
work is exactly the payload prefix and no primary-slot map is needed.

Without closure, `selected_count == primary_count == min(S, N-first)`.

With closure, selected IDs are the unique union of primaries and every
nonphysical direct face neighbor in TOP columns `0..5`. Closure is not recursive.
Closure-only support occupies
`chunk_block_ids[primary_count:selected_count]` in first-discovery order while
scanning primaries ascending and faces low-to-high. A support ID that later
becomes primary is promoted into the primary prefix without changing the
relative order of remaining support.

The planner greedily accepts a next primary exactly when its union fits; closure
size is monotone, so the result is the maximal feasible interval. If the first
primary plus its closure cannot fit, it raises `ValueError` before mutation.
Otherwise the first rejected primary causes a normal chunk boundary. The output
suffix from `selected_count` onward is preserved.

`minimum_face_closed_slots(face_neighbor_ids)` returns the maximum over blocks
of one plus its nonphysical face count. Capacity at least this value guarantees
progress for a complete face-closed traversal.

Full padded halos require diagonal source interiors, so STO-002 also provides:

```text
plan_level1_halo_chunk(
    first_primary_id,
    face_neighbor_ids,
    chunk_block_ids,
) -> (primary_count, selected_count)
```

It preserves the same primary-prefix, maximality, promotion, first-fit error,
support-order, suffix-preservation, and ownership rules, but closure is the
complete clipped one-block `3x3x3` neighborhood of every primary. Directions
are discovered with x varying fastest, then y, then z: `dz=-1..1`,
`dy=-1..1`, `dx=-1..1`; center is skipped as support because it is the primary.
Each direction ID is derived by walking nonzero faces in fixed x, then y, then z
order. TOP-001 commutation makes the resulting ID independent of walk order.

`minimum_halo_closed_slots(face_neighbor_ids)` returns the largest clipped
`3x3x3` closure in the topology. It is at most 27, so capacity 27 guarantees
progress on every Cartesian 3D level-1 grid. HAL-002 must reject any allocated
lower or upper halo width larger than the corresponding interior block extent;
otherwise a target cell could require a source two blocks away and one-block
closure would be insufficient.

TOP semantic validity is a precondition for direct-face planning, full-halo
planning, and both minimum-closure helpers; relation values are not range-
validated or rescanned for every chunk. Without closure, only the table's block
count and array boundary are used; relation values are not consulted.
Type/dtype, shape, layout, range, bool, capacity, writability, and overlap errors
are rejected before mutation. Inputs are borrowed and unchanged; outputs and
pointers are never retained.

## Coverage And Validity

Starting at zero and advancing by `primary_count` covers every global block
exactly once as a primary. Support blocks may recur across chunks and are never
consumer work unless also in the primary prefix. Planned IDs are unique within
the selected prefix.

The reusable payload has FND-001 canonical layout. STO-001 gathers
`chunk_block_ids[:selected_count]` into its first `selected_count` slots and
defines the translated valid box. Payload and ID suffixes beyond the returned
counts retain unspecified reusable state.

Direct face closure supplies face-only exchange participants. Full halo closure
supplies HAL-002/SAM-003 edge and corner source interiors. Ordered propagation
and halo values remain HAL responsibilities.

## Out-Of-Core Composition

A read-only C-order `numpy.memmap` may be passed directly as STO-001 backing.
Iterating plans into fixed managed arrays proves that the complete field payload
need not be eagerly resident or copied into a full NumPy allocation. The mapped
file may exceed `budget_bytes`; the managed payload and ID arrays may not.

This is a virtual-memory/out-of-core guarantee, not a hard RSS cap: OS page cache
and page-fault behavior are measured separately where available. A future native
pread source may strengthen resident-set control without changing chunk or
workspace semantics.

## Exactness And Performance

Planning and coverage are discrete and exact. Reference comparisons require
identical counts, order, closure union, maximality, suffix preservation, and
exactly-once primary coverage. No numerical tolerance applies.

No-closure planning is `O(primary_count)`. Face-closed planning uses linear
membership in the bounded ID prefix, requires no heap scratch, and is measured
by planner runtime, capacity utilization, selected/primary amplification, chunk
count, managed bytes, and composed STO-001 throughput. Parallel planning is not
relevant to this deterministic metadata primitive.

## Immediate Composition

STO-001 performs exact planned transfers. TOP-001 supplies face walks. RED-001
consumes no-closure exactly-once primary chunks. Face-only consumers use direct
closure; HAL-002 and SAM-003 consume full halo closure. INT-001 uses the memmap
path to demonstrate bounded M0 execution.
