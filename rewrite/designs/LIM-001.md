# LIM-001 Design: Cartesian Three-Point Limited Slope

## Problem And Current Rule

Current ratio-two prolongation repeatedly evaluates one scalar three-point
limiter.  It separately forms left and right differences, forms their centered
average, chooses a sign branch, and clips by the same-sign one-sided values.
Coordinate/index construction, coarse reach, eta, x/y/z reconstruction, scratch
assembly, and halo scheduling surround that rule but vary independently.

## Alternatives

An array-region slope kernel would decide axes, regions, output mutation,
materialization, caching, and scratch lifetime before a consumer demonstrates
that stored slopes are useful.  Keeping the rule only inside a fused
prolongation loop would prevent independent semantic validation.  A generic
minmod utility would obscure current nonfinite and signed-zero behavior.

Use one validated scalar operation backed by a shared Cython
`inline noexcept nogil` rule.  The simple operation freezes semantics and is
substitutable; PRL-001 will call the inline rule without Python callbacks or
slope arrays.  A cached/array strategy remains a later measured alternative.

## Decomposition Record

Responsibility: compute the exact current limited slope from explicit binary64
left, center, and right values.

Owned decisions: separate left/right differences; centered-average operation
order; positive/negative/zero branch; comparison-based absolute/minimum rules;
same-sign clipping; exact positive-zero fallback; scalar validation and return.

Explicitly non-owned decisions: coarse indices or axis; valid reach; fine or
coarse coordinates; ratio-two phase/eta; active dimensions; x/y/z
reconstruction; region/output mutation; slots/fields/global IDs; relation or
support policy; restriction; coarse workspace validity/layout; slope arrays or
caches; physical rules; backend; scheduling; parallelism; or 2D.

Inputs and output: three exact Python `float` or NumPy `float64` scalars and one
exact Python-float binary64 result.  All binary64 values are valid.

Mutation and ownership: no mutable output, input mutation, retained pointer,
cache, or size-dependent scratch.  The public operation returns one ordinary
Python float; the shared inline rule allocates nothing.

Access pattern and reach: three already-selected scalar values.  Selecting the
one lower/upper coarse neighbor needed by PRL is not a LIM decision.

Independent reference and invariants: manual NumPy-scalar operations and
ordinary comparisons; monotone finite minmod behavior; exact positive zero at
plateaus/extrema/NaNs; subnormal preservation; nonfinite/overflow branch cases;
random finite triples; and RST-produced coarse values.

Immediate producer and consumer: RST plus later workspace assembly supplies
explicit coarse values; PRL consumes the inline rule.  LIM does not materialize
the producer/consumer regions.

Kernel and composed measurement boundary: validated/unchecked/reference scalar
calls per second, fixed traced allocation, and branch distributions.  The
meaningful hot-path metrics—inline slopes and prolonged cells per second,
coarse reach scaling, bounded RST/workspace/PRL composition, and cached versus
inline strategies—belong to PRL.

Five-question result: yes/yes/yes/yes/yes.  Scalar behavior is singular,
independently testable/substitutable, directly measurable for boundary cost,
and independently composable through a static inline rule without storage or
execution policy.

## Performance Gate

The standard descriptive workload is one million calls cycling a fixed branch
mix: positive/negative monotone, extremum, plateau, NaN, infinity, overflow,
and subnormal cases.  Compare validated production, unchecked Cython, and the
manual scalar reference in rotating order; exact output bits/classes are hard
gates.  Record calls/s and traced retained/peak bytes.

This scalar timing measures boundary overhead, not PRL throughput.  At PRL,
compare the inline rule with any credible cached-slope variant on the same
cells/fields/regions.  Investigate >10% and block a reproduced >20% composed
regression absent a documented memory/complexity benefit.  Do not add array
materialization or parallel machinery before PRL shows a material benefit.
