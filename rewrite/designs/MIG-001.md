# MIG-001 Design: Supported Feature Migration

## Problem

M0--M3 define a sound AMR numerical-core sequence, but the current canonical
source also owns format I/O, uniform construction, dataset/field lifecycle,
derived fields, exports, independent scientific helpers, runtime/build behavior,
and public APIs. Declaring the numerical core complete would leave the rewrite
isolated and never establish production replacement.

## Alternatives And Review

A file/method checklist is concrete but rewards mechanical translation,
duplicates legacy code, and cannot prove user-observable parity. A public-API
list alone misses format, failure, memory, and build behavior. An open backlog
has no verifiable cutover condition.

The selected approach tracks feature families from current authority through
explicit disposition, contract, tests, benchmark/workflow evidence, and final
replacement. Legacy code remains evidence unless it uniquely owns supported
behavior. Independent review agreed that M0--M3 should remain the semantic-core
axis while native real-data slices, operators/derived fields, I/O/export,
dataset/API integration, and packaging/cutover become explicit later stages.
