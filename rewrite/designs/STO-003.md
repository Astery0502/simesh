# STO-003 Design: Functional Block Transfer Adapters

## Problem

STO-001 correctly transfers canonical resident arrays, and `numpy.memmap`
works because it is an ndarray subclass. INT-001 nevertheless names arrays
directly, so a native AMRVAC reader, cache, HDF5/Zarr source, or another
framework would require editing the executor even though halo and compute
kernels only need the gathered canonical workspace.

The substitution boundary must remain coarse grained. Python callbacks inside
Cython cell/block loops would make performance and ownership opaque, while a
class hierarchy or global registry would introduce framework before concrete
semantics require it.

## Alternatives

A source/sink class with methods is familiar but hides state behind object
history and encourages inheritance. A global singledispatch registry hides the
selected implementation and makes validation dependent on process state.
Passing bare callables to every executor keeps dispatch visible but leaves
shape, state lifetime, and memory-alias information detached.

The selected design uses small frozen data descriptors. Each descriptor carries
explicit backend state, canonical shape, one read or write function, and any
NumPy arrays that participate in alias checks. Free functions invoke the
callable once per chunk. Array factories adapt resident arrays and memory maps
through STO-001; future backends implement the same transfer contract without
entering numerical kernels.

## Integration Direction

Add `execute_level1_m0_from_blocks(...)` over reader/writer descriptors and
retain the stable INT-001 array operation as a wrapper. The wrapper preserves
the established ndarray/memmap behavior. Full-capacity and bounded plans use
the same functional backend operation and must remain numerically identical.

Custom callbacks are trusted adapter code and may perform external I/O. Common
shape, topology, budget, output, and alias preflight remains in the executor;
an external I/O failure after mutation begins is not silently described as an
atomic transaction. Framework-specific compute remains a later capability and
must implement full kernel contracts rather than bypassing them through an
array-like label.
