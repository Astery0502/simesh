# OPR-001 Design: Pointwise Field Transform

## Alternatives

A callback, expression tree, or runtime kernel registry would make pointwise
operators superficially generic but violates the rebuild-based extension model
before any shared interface is proven. In-place source/output aliases can save a
buffer but complicate ownership and atomic validation. A fused backing-storage
kernel avoids transfers but couples scientific arithmetic to STO selection and
sink policy.

Use one concrete transform already exercised by the current derived-field path:
`left - scale*right` (for example `e - 0.5*rho`). The operation takes explicit
source and destination field positions and translated spatial regions, forbids
overlap, and writes into caller-owned canonical output. It establishes the
pointwise zero-reach contract without inventing a dynamic operator system.

The first Cython form uses separate multiply then subtract operations and a
simple scalar reference. Benchmark the independent gather/compute/scatter path
before considering an in-place or fused storage variant.

Independent behavior recovery added two numerical boundaries before freezing
the contract: only Python `float` and NumPy `float64` coefficients are accepted,
and finite inputs whose product overflows belong to IEEE nonfinite evidence, not
the finite error bound. Relative error is reported only away from cancellation;
signed zero and nonfinite results use exact classification/sign checks.

## Optimization Result

The retained Cython loop uses prevalidated bounds, fixed multiply/subtract
rounding, and no scratch. Larger cases reach about 20.4 GB/s effective
read/read/write bandwidth. A complete bounded gather/compute/scatter traversal
at capacity 1,024 reaches 504 Mvalue/s versus 543 Mvalue/s for whole-array NumPy
while avoiding NumPy's additional 16 MiB product temporary. The small remaining
gap does not justify in-place alias rules or coupling the operator to STO
backing, so no fused variant is retained.
