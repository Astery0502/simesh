# STO-002 Design: Bounded Chunks And Workspace

## Problem

STO-001 can transfer arbitrary selections but does not choose them or prove a
bounded reusable payload. Streaming reductions need contiguous exactly-once
primary coverage; face exchange additionally needs neighboring support blocks.

## Choices Considered

A fixed primary capacity divided by a worst-case closure wastes most workspace
because adjacent closures overlap. Full 3×3×3 closure anticipates corner halo
strategy and may require an N-sized marker or hash-like membership structure.
Direct face closure is sufficient to stage face exchange; HAL-002 owns diagonal
derivation and propagation order.

A source class hierarchy would add protocol before a second source exists.
NumPy memory maps already satisfy STO-001's strict array boundary and provide a
real out-of-core composition without becoming a file-format contract.

## Selected Direction

Compute exact slot capacity from caller buffer bytes. Plan the maximal ascending
contiguous primary interval that fits, optionally unioned with direct TOP-001
face neighbors. Store primaries first and unique closure-only support afterward.
Use the caller ID array itself for membership and stable support ordering; no
hash, bitmap, or selection-sized scratch is introduced.

Gather planned IDs through STO-001 into one reusable payload. Demonstrate
streaming from a read-only C-order `numpy.memmap`, while stating explicitly that
the budget covers managed arrays rather than OS page-cache residency.

## HAL-002 Integration Evidence And Contract Extension

HAL-002 requires an interior source block for every padded primary cell. A
primary edge/corner cell crosses two or three block axes, so its source is a
diagonal block. Direct face closure contains only the primary and six face
neighbors; for an interior primary of a `3^3` grid it has seven IDs and omits all
12 edge and eight corner blocks. Staged face copying cannot create those values
unless the omitted diagonal interiors are also loaded.

Independent contract review agreed that no experiment was needed. The stable
extension retains `plan_level1_chunk(...)` unchanged and adds
`plan_level1_halo_chunk(...)`. The new planner uses the same primary-prefix and
support-order contract but unions the complete clipped one-block `3x3x3`
neighborhood of each primary, deriving all directions by commuting TOP face
steps. It uses the caller ID buffer for membership and no hash/bitmap/scratch.
This changes managed capacity only through the larger selected count; the
existing byte formula remains exact. HAL-002 and SAM-003 are affected; no-closure
RED-001 and direct-face users retain their existing behavior.
