# WSP-001 Design: Canonical Workspace Accounting

## Trigger And Inventory

The decomposition audit classified STO-002 Yellow because it groups four
independently variable decisions: workspace accounting, primary traversal,
direct-face closure, and full-halo closure.  REL-001 now makes refined support
planning imminent, so the recorded trigger has fired.

This checkpoint extracts only the first decision.  Existing STO-002 behavior,
tests, and callers remain frozen; `simesh_rewrite.chunking` keeps compatibility
entrypoints that delegate to the new canonical owner.  Primary traversal and
each closure policy remain untouched for later incremental extraction.

## Alternatives

Leaving accounting in `chunking` would keep storage size semantics coupled to
level-1 planning.  A general scratch-manifest or dynamic workspace registry
would add machinery and invite unrelated executor state into one formula.

Use one small `workspace` module for the exact canonical payload-plus-ID bytes
and its algebraic inverse.  Forward and inverse operations stay together
because both own the same decision about which arrays count per slot.
A generic public per-slot arithmetic layer is deferred until a second executor
needs it; INT-001's richer formula remains explicitly executor-owned.

## Decomposition Record

Responsibility: compute exact managed bytes for one canonical float64 payload
workspace plus one int64 global-ID vector, and invert that formula under an
explicit block-count limit.

Owned semantic decisions: positive field/spatial dimensions; exact bytes per
slot; nonnegative budget/capacity/block limit; floor division and clamp;
signed-int64 representability; scalar/shape validation and error classes.

Explicitly non-owned decisions: allocation, primary traversal, progress,
exactly-once coverage, any support closure, topology, union/promotion/order,
slot mapping, transfer, payload values, backend, mapping, RSS/page cache, I/O,
or extra output/coarse/relation/reduction scratch.

Inputs and outputs: Python/NumPy integer scalars and one borrowed C-contiguous
`int64[3]` shape; exact Python integer result; no mutable output.

Mutation and ownership: pure scalar operations; nothing is mutated or retained.
No array- or input-size-dependent scratch is used; fixed Python scalar/call
objects are permitted and measured.

Access pattern / halo reach: not applicable; workspace accounting has no
payload access or topology reach.

Independent reference or invariant: Python arbitrary-integer formula; forward
linearity; inverse byte-boundary maximality; exact equality to actual NumPy
payload plus ID `nbytes`; old/new/error conformance.

Immediate producer and consumer: FND-001 supplies canonical payload/ID layouts;
STO-002 compatibility wrappers and current bounded executors consume the result.
INT-001's richer multi-array formula remains separate.

Kernel and composed measurement boundary: descriptive calls/s and fixed Python
allocation plus exact actual-array/budget composition.  Scaling is constant
because the shape rank is fixed at three.

Five-question result: yes/yes/yes/yes/yes.  Forward and inverse accounting are
one algebraic responsibility; all traversal and closure decisions remain split.

## Compatibility Baseline

Before extraction, all 12 STO-002 tests pass.  On the retained Apple arm64
probe, forward and inverse calls take 2.60 and 2.70 microseconds respectively,
with zero retained traced bytes and a 1,053-byte traced peak for one pair.  The
canonical function and legacy wrapper must remain bit/error identical and must
not materially regress this fixed-cost boundary.
