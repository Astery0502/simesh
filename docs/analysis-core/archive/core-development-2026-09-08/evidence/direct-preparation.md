# 直接准备与重复分析的效率改进

日期：2026-09-08。对照源码为 `d922e29`；候选为本轮未提交实现。
本轮按用户要求优先效率与算法，不扩展缓存层、存储分配器或执行后端。

## 实际改动

- `open_prepared(..., bounds=(lower, upper))` 与 `prepare_region` 提供一次区域准备。
  选择相交完整叶块，支撑继续来自原始 AMR 网格，不在裁剪处制造物理边界。
  不传 bounds 时仍使用规范 bulk 驻留准备。
- analysis 的 provider 直接组织准备批次，不再经过独立 RHC 执行器的整请求
  预检查与消费者回调。每批只生成一次邻接、支撑和槽位，再执行原传递运算。
- `global_curl` 直接遍历固定批次，取消该顺序遍历对池年龄、淘汰和借用状态的依赖。
- 编译追踪在同一叶块内复用 node 定位，只在跨块时重新查树；最终 RK 提议位置
  只检查物理域，下一次采样再解析叶块。RK、插值、twist 和接受前缀算术不变。

## 验证边界为何可以简化

`make_source` 已验证整份森林几何、全接触 2:1 平衡、偶数且至少四格的块形状。
本源固定两层 halo、continuous 物理边界和 exact-phase/minmod 策略，并要求几何
在源生命周期内不变。这些条件不需要在每批传递前重新用完整独立入口证明。

每次 fill 仍检查叶块和字段请求、输出布局、源/输出别名及生命周期；支撑绑定仍有
活动槽位检查，底层读取仍验证记录与文件状态。数值传递使用原内核和原操作次序。
所有结果只在整次 prepare 成功后发布；池缺失仍先失效被覆盖槽，再在成功后发布键。
失败时私有暂存可被部分写入，但不会成为已完成的 `PreparedFields`。

原 rewrite 的独立 RHE/RHC 入口及其预检查、写入和失败约定没有修改。这里调整的是
analysis 自己的准备编排边界，并非给旧入口添加“跳过检查”开关。

## 比较方法

同一进程交错运行修改前的 native 扩展/准备器与当前实现；每组先各执行一次，随后
按相反次序交错计时。追踪五次，准备和全域 curl 三次。读取受操作系统页缓存影响，
不称为冷磁盘。旧源和新源保持同一策略、字段顺序、支持容量和输出范围。

- 制造场：已有混合级别螺旋磁场，2048 种子、600 步、步长 0.005，比较一/四工作者；
  另比较 128 种子的 twist 与保存轨迹。
- WENO 局部：原始 `data/weno509_sub_0000.dat`，全域 22,614 叶块；256 种子、128 步。
  种子取自中心选区的 112 个叶块中心，包含重复坐标；不是 256 个独立空间位置。
  在读取数值前由种子范围和最大弧长选择一个固定盒，得到 1,142 个准备目标叶块。
  比较完整准备数组以及追踪位置、长度、步数、终止信息等所有结果数组。
- 全域 D：所有 22,614 叶块的三分量 curl，共 67,842,000 个值，随后生成 128² 轴向
  和 96×80 斜向切片。逐批检查所有值，不用局部校验和替代完整比较。

初次使用过小的任意中心盒时，WENO 追踪正确返回覆盖不足。最终工作负载在读取前
使用最大弧长选区，不根据已知轨迹偷选覆盖，也没有在计算中自动扩大区域。

原始记录位于 `benchmark-results/analysis-core/`：`direct.json` 是仅修改定位与
顺序 curl 的中间比较，`direct-preparation.json` 加入直接准备，`direct-final.json`
包含最终全域 D 对照。环境、每次时间、准备统计、源与结果尺寸和进程 RSS 保留在
原始 JSON 中。不同轮次的时间不拼接成加速声明。

## 最终同机结果

以下均取 `direct-final.json` 同一轮交错测量的中位数。环境为 macOS arm64、
Python 3.11.14、NumPy 2.4.4、默认非 OpenMP 构建；线程比较使用已有线程池。

| 完整操作 | 修改前 | 修改后 | 比值 |
| --- | ---: | ---: | ---: |
| WENO 固定区域准备，1,142 个目标叶块 | 1.2320 秒 | 0.3151 秒 | 3.91 倍 |
| WENO 驻留追踪，256 种子 × 128 步 | 17.651 毫秒 | 8.657 毫秒 | 2.04 倍 |
| WENO 全域 curl 加两切片，单工作者 | 33.8327 秒 | 16.2627 秒 | 2.08 倍 |
| 制造场 2048 种子 × 600 步，一工作者 | 0.4404 秒 | 0.3945 秒 | 1.12 倍 |
| 相同制造场，四工作者 | 0.1389 秒 | 0.1043 秒 | 1.33 倍 |
| 制造场 128 种子 twist 加轨迹 | 29.150 毫秒 | 22.858 毫秒 | 1.28 倍 |

准备改进的比较采用同一组选区、相同顺序和每批 256 支撑槽位；两边均产生相同
19 批、4,676 次支撑叶块装载、57,458,688 字节字段传输。每个准备值逐值相同。
这是避免重复编排与预检查的改善，没有靠减少读取量或改变数值操作。

全域比较包含约 543 MB 的派生结果和两张切片的实际生成，所有 67,842,000 个值
及切片逐值相同。对应单次时间分别为旧 31.77/33.83/36.30 秒、新
15.65/16.26/18.76 秒，有主机与读取波动；不把某一次最快值作为承诺。
这组倍率同时包含直接准备和顺序 curl 简化，不能全归因于删除缓存池。

该轮区域第一次准备约 0.921 秒，其中读取约 0.657 秒；连同打开数据源、选区、首次追踪
约 0.978 秒。后续重复准备中位数 0.315 秒，不把它当成首次文件访问成本。
公共 `open_prepared(bounds=...)` 在已有系统缓存下约 0.497 秒，其默认支撑容量
为 128，与上述固定 256 槽位的比较条件不同。

区域结果持有 47,551,072 字节准备场，派生场另有 27,598,048 字节。整个比较进程
观测峰值 RSS 1,179,598,848 字节，包含为了对照同时保留的新旧结果；不代表用户
单次分析的必需占用，也不证明更大输入的吞吐。没有扩大既有计算工作者上限。

## 如何解释结果

一次准备再消费，不保证比动态池少准备块。当前选区比实际轨迹工作集大；可容纳
全部访问 owner 的池在首次补齐后，同样能做到零重复准备。因此新区域入口的价值
是显式、稳定且可组合的准备流程；准备器和定位算法的同输入对照才用于性能倍率。

具体来说，这组轨迹只访问 246 个 owner。256 槽位池首次执行约 0.091 秒，随后
约 9 毫秒且零新准备；固定区域却准备了 1,142 个目标块。保留这一反例：不能用
驻留追踪的低延迟掩盖扩大选区的首次成本，更不能宣称区域方案普遍替代有限容量路径。

局部准备仍可能跨批重复读取支撑块，仍调用部分 Python 传递编排。没有采用新的
重构、减少 halo 宽度、改变 minmod 或使用持久 fill plan 来取得本轮改善。全域
字段能放下时，规范驻留准备继续保留，不因有限容量路径改善而更换它。

内存统计用于说明测量条件，不是新的存储设计或 RSS 保证。工作区释放、几何
所有权合并、更大输入和额外工作者规模均不由本轮宣称完成。

## 复现

比较前在 `benchmark-results/analysis-core/direct-baseline/` 保存 `d922e29` 对应的
默认构建 `native*.so`、`src/simesh/analysis/providers.py` 和
`src/simesh/analysis/global_fields.py`。不要用新文件覆盖旧基线。

```sh
make build PYTHON=.venv/bin/python
PYTHONPATH=src:rewrite/src:scripts:tests/analysis:rewrite/benchmarks .venv/bin/python -m analysis_core.benchmark_direct --baseline-dir benchmark-results/analysis-core/direct-baseline --output benchmark-results/analysis-core/direct-final.json --full-curl
PYTHONPATH=src:rewrite/src:scripts:tests/analysis:rewrite/benchmarks .venv/bin/python -m unittest discover -s tests/analysis -v
PYTHONPATH=src:rewrite/src:scripts .venv/bin/python -m analysis_core.validate_install --output benchmark-results/analysis-core/direct-install.json
```

脚本拒绝覆盖已有输出；重复测量需换一个输出文件名。
