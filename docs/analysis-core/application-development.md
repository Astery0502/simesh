# 应用层开发指引

面向开发协作。当前核心已固定，后续从用户需要的结果出发消费已有数据。
入口是[固定核心设计](next-generation-design.md)和新包
[调用说明](../../analysis-core/README.md)，不必先阅读历史探索或验收报告。

## 从一个实际流程开始

先说明应用要回答什么问题、需要哪些字段/区域、输出给谁，以及怎样呈现结果。
随后选择现有 Source、Fields 和消费者完成一个代表性流程，再按实际需求扩展。
避免预先建立庞大的应用框架或把文件读取、所有科学模型和全部输出统一到一个会话对象。

| 应用需要 | 可直接使用 |
| --- | --- |
| 原始数值、选区与字段检查 | `open_amrvac`、`read_fields`、`Selection` |
| 同一数据上的重复计算 | 一次 `prepare` 后复用 `Fields` |
| 图像/截面/固定网格消费 | `sample_plane`、`iter_uniform` |
| 轨迹与沿线诊断 | `trace`、`iter_traces`、`retrace`、显式 curl |
| 视角图像 | `integrate_los`、`integrate_thermal_los` |
| 既有 Dataset 或文件交付 | `source_from_dataset`、`write_amrvac` 和兼容接口 |

应用需要明确字段含义、单位、区域覆盖和结果状态；检查失败/缺失覆盖，
不把未完成结果显示成有效科学产品。准备场、派生场与输出的生命周期按实际
使用安排，不因“可以保留”就同时持有所有中间数组或全部流式切片。

## 用与改动相称的检查

- 界面、展示和简单组合：运行一个代表性流程，检查用户可见结果。
- 改变单位、物理量或输出含义：用相应的已知结果或参考例子验证。
- 修改核心行为：检查受影响的约定和已有核心测试；Cython 改动才需要重新构建。
- 出现实际速度/内存问题或作出性能承诺：围绕该问题测量，不默认运行完整历史矩阵。

默认单任务推进。独立评审或额外任务用于确有价值的具体问题，不作为每次应用
改动的固定步骤。常规开发记录只需写清结果、关键选择和必要验证，不沿用 N1–N4
的阶段验收材料规模。

完整历史材料在[归档](archive/README.md)。它们用于解释来源和旧决策，
不自动带入新的应用范围、待办或审批要求。
