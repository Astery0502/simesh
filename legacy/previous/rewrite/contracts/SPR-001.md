# SPR-001 Contract: Explicit Selected-Primary Refined Support Planning

## Responsibility

SPR-001 plans the maximal prefix of an explicit strictly increasing
selected-primary stream whose unique union of REL-001 source leaves fits caller
capacity.  It preserves
STO-004 support union/order/capacity semantics but does not define primary
selection, dense traversal, relation meaning, direction choice, geometry,
source-slot mapping, numerical transfer, payload I/O, cache, or scheduling.

## Stable Operation

```text
plan_selected_refined_support_prefix(
    primary_leaf_ids,
    first_primary_position,
    leaf_count,
    source_counts,
    source_leaf_ids,
    selected_leaf_ids,
) -> (primary_count, selected_count)
```

`primary_leaf_ids` is borrowed read-only native-endian C-contiguous `int64[P]`,
is strictly increasing with every ID in `[0,leaf_count)`, and defines canonical
sparse SFC order.  Gaps are allowed.
`first_primary_position` is a nonnegative signed-int64-representable integer in
`[0,P]`.  `leaf_count` is a nonnegative signed-int64-representable integer.

`selected_leaf_ids` is caller-owned writable C-contiguous `int64[S]`.  Let

```text
C = min(S, P - first_primary_position).
```

`source_counts` is borrowed C-contiguous `uint8[C,D]` and `source_leaf_ids` is
borrowed C-contiguous `int64[C,D,4]`.  Row `r` is the unchanged REL source row
for `primary_leaf_ids[first_primary_position+r]`.  Counts are in `[0,4]`, active
source IDs are in `[0,leaf_count)`, and inactive columns are exact `-1`.
Direction order is caller policy and remains fixed across one traversal.

The companion progress-bound operation is:

```text
maximum_selected_refined_support_slots(
    candidate_leaf_ids,
    leaf_count,
    source_counts,
    source_leaf_ids,
) -> slot_count
```

`candidate_leaf_ids` has the same borrowed strictly increasing in-range
representation as `primary_leaf_ids`.  Its REL arrays contain exactly one row
per candidate and obey the same count/source/sentinel rules.  For each row the
operation forms the unique set containing that candidate plus all active REL
sources, then returns the maximum set size over the rows, or exact zero for an
empty input.  It does not model cross-primary promotion and therefore provides
the exact minimum capacity for guaranteed one-primary progress.  Taking the
maximum of results for any row partition gives the result for the unpartitioned
input.  The operation borrows every input, allocates no size-dependent storage,
retains nothing, and uses the same representation, range/order, relation-value,
and scalar error categories as the planner.

## Exact Plan

Consider candidates in primary-vector order.  Accepted candidates occupy the
output prefix in that same order.  For each candidate trial:

1. remove the candidate from existing support if present;
2. append it to the primary prefix;
3. scan directions and active source columns in row order, appending each ID
   not already primary or support;
4. accept only if the unique union fits `S`.

The first nonfit raises
`ValueError("selected capacity cannot fit the first refined support closure")`
without mutation.  A later nonfit ends the chunk normally.  Success returns a
maximal primary prefix and selected count, and preserves
`selected_leaf_ids[selected_count:]` bitwise.  Support may recur across chunks;
advancing the position by `primary_count` visits each explicitly selected
primary exactly once and never invents an intervening leaf.

The exact lookahead length `C` proves maximality: a rejection is represented,
end is represented, or `S` distinct primaries fill capacity.  At stream end,
zero relation rows are required and `(0,0)` is returned without mutation.
Before end, zero capacity raises after complete representation validation.

## Validation And Ownership

Validate scalar and array representations, position/range, exact relation-row
shape, all output/input nonoverlap, complete primary range/strict order in one
linear pass, and all count/source/sentinel values before mutation.  Wrong
scalar/array kinds or dtypes raise `TypeError`; invalid layout, range, order,
duplicate, shape, overlap,
relation value, or capacity raises `ValueError`; scalar overflow raises
`OverflowError`.  The first out-of-range or non-increasing entry is reported.
Inputs are unchanged and nothing is retained.

The checked wrapper validates the complete contract.  After an executor has
validated the unchanged primary vector and REL windows, it may call the
explicit unchecked kernel for each chunk.

## Exactness, Evidence, And Cost

Plans are discrete and exact.  Evidence covers sparse ascending IDs, promotion,
duplicates in relation sources, first/later nonfit, suffix/end, zero directions,
dense STO-004 equivalence, selected-only gather composition, exact progress
bounds and partition invariance, and representative atomic contract errors.
The kernel uses bounded linear membership with a fixed balanced-source stack
and no selection-, leaf-, or payload-sized internal allocation.

SPR-001 is composition-only.  Measure it first in selected REL/plan/gather by
primary/support counts, amplification, relation/output bytes, reader calls,
useful/read bytes, validation cost, and unchecked planning cost.  A hash or
dense marker is reopened only when that real composition shows membership
planning is material.

## Immediate Composition

An ROI or explicit leaf selector supplies sorted `primary_leaf_ids`; REL supplies the
bounded rows.  RSL consumes the resulting selected IDs and STO-001/003 gathers
only accepted primaries plus support.  Dense full traversal may continue to use
STO-004 unchanged.
