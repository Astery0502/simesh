# HCL-001 Contract: Complete Level-1 One-Block Halo Closure

## Responsibility

HCL-001 plans the maximal dense ascending primary prefix whose unique complete
clipped level-1 one-block `3x3x3` support union fits explicit caller capacity,
and computes the exact capacity sufficient for one such closure everywhere.  It
defines no byte accounting, topology construction, relation masks/slots, halo
values/reach, refined support, payload, backend, or scheduling.

## Stable Operations

```text
plan_level1_halo_closed_prefix(
    first_primary_id,
    face_neighbor_ids,
    selected_ids,
) -> (primary_count, selected_count)

minimum_level1_halo_closed_slots(
    face_neighbor_ids,
) -> slot_count
```

`face_neighbor_ids` is borrowed read-only native-endian C-contiguous TOP-001
`int64[N,6]`.  TOP semantic validity and face-step commutation are unchanged
upstream preconditions.  HCL validates representation but does not repair or
range-rescan relations per call; this precondition is required for unchecked
multi-step pointer safety.

`selected_ids` is caller-owned writable native-endian C-contiguous `int64[S]`;
its length is explicit capacity.  `first_primary_id` accepts Python/NumPy
integer scalars except booleans/rank-zero arrays, fits signed int64, and lies in
`[0,N]`.  Output may not overlap the face table.  Inputs are unchanged and no
pointer/state is retained.

## Direction And Face-Walk Order

For each primary, directions occur in exact x-fast order:

```text
for dz in (-1, 0, 1):
    for dy in (-1, 0, 1):
        for dx in (-1, 0, 1):
```

Center is already the primary and is skipped during support discovery.  For
each noncenter direction, begin at the primary and walk each nonzero axis in
fixed x, then y, then z order using TOP face columns `(0/1,2/3,4/5)`.  If any
step returns physical sentinel `-1`, omit the entire direction.  Otherwise the
final ID is that clipped one-block neighbor.  TOP commutation makes alternate
walk orders equivalent, while HCL freezes x/y/z for deterministic evidence.

## Exact Closure Plan

Consider dense candidates from `first_primary_id` upward in PRI-001 order.
Accepted primaries occupy the exact ascending prefix.  Closure-only support
follows in stable discovery order.  For each candidate, form a trial:

1. remove the candidate from existing support if present, preserving other
   support order;
2. append it to the primary prefix;
3. discover its 26 directions in the order above and append each nonphysical ID
   not already primary/support;
4. accept the trial exactly when its unique union fits capacity.

If the first candidate closure cannot fit, raise
`ValueError("chunk capacity cannot fit the first halo closure")` before any
write.  A later nonfitting trial ends the chunk normally with the prior plan.
The result is the maximal feasible dense primary prefix.

On success, `selected_ids[:primary_count]` is the PRI interval and
`selected_ids[primary_count:selected_count]` is unique support.  For every
primary, selected IDs contain every in-domain block whose coordinate differs by
at most one on every axis.  Support is nonrecursive and never consumer work.
The suffix `selected_ids[selected_count:]` is bitwise preserved.  Successive
calls advancing by `primary_count` cover every ID exactly once as primary.

At end `first_primary_id == N`, return `(0,0)` without mutation for any
capacity.  Before end, zero capacity raises `ValueError` before policy execution.

## Minimum Progress

`minimum_level1_halo_closed_slots(...)` counts, for each row, every one of the
27 directions including center whose fixed face walk remains nonphysical, and
returns the maximum or zero for an empty table.  Under valid Cartesian topology
this equals the clipped `3x3x3` coordinate-neighborhood size and lies in
`[1,27]` for nonempty input.  A `1x1x1` topology gives one; a fully interior
row gives 27; singleton axes clip the product accordingly.

Capacity at least the returned value guarantees every unfinished planner call
accepts a primary; a smaller capacity fails for a call starting at an argmax
row.  HCL does not choose capacity.  HAL separately rejects a halo width larger
than the corresponding block interior because such reach can cross two blocks.

## Validation, Errors, And Atomicity

Canonical validation order is face table, selected output, first scalar, range,
overlap, and unfinished positive capacity.  Wrong objects/dtypes or scalar kinds
raise `TypeError`; invalid rank/layout/writability/range/overlap/capacity raise
`ValueError`; scalar overflow raises `OverflowError`.  The minimum helper
validates only face-table representation.

All Python-boundary and first-fit failures preserve the entire output.  A later
normal boundary preserves only the suffix after returned `selected_count`.

## STO-002 Compatibility

Existing `minimum_halo_closed_slots(...)` and
`plan_level1_halo_chunk(...)` delegate after preserving their exact validation,
messages, counts, IDs, suffix, end behavior, and errors.  The no-closure and
direct-face wrappers remain PRI-001 and FCL-001.  After HCL completion, STO-002
is a compatibility-only composition rather than a remaining semantic owner.

## Independent Evidence

The independent reference uses Python primary/support lists and explicit
x/y/z face walks.  Coordinate TOP fixtures provide a separate clipped
Chebyshev-neighborhood oracle.  Evidence covers empty/singleton/nonsymmetric
roots; exact center/face/edge/corner order; all clipping; commutation;
promotion/overlap/maximality; suffix/end/first-fit atomicity; minimum/progress;
exhaustive/random full traversal; scalar/table/output/alias errors and
precedence; wrapper conformance; HPL source-slot sufficiency; and INT artifact/
reduction equality across capacities.

## Performance And Memory

HCL evaluates 26 directions per trial plus linear support membership.  The
production kernel retains at most 26 newly discovered IDs on a fixed C stack so
accepted trials commit without a second face walk.  It uses no hash, bitmap,
dense marker, callback system, or size-dependent scratch.
Measure primaries/s, selected IDs/s, chunks, amplification, utilization,
capacity scaling, minimum-helper rate, wrapper overhead, fixed allocation,
small-reference ratio, and INT pass-two timing/artifacts.  Payload/RSS/I/O and
parallel scaling are composed executor metrics rather than HCL kernel metrics.
Canonical versus retained wrapper and INT pass two are same-run comparators;
exact IDs/artifacts are hard gates, a regression above 10% is investigated, and
a reproduced regression above 20% blocks completion absent a documented
runtime-memory trade-off.

## Immediate Composition

PRI-001 supplies candidate identity and TOP-001 supplies face steps.  The M0
pipeline consumes HCL directly for full-halo preflight/pass two, while preserved
wrappers serve HPL/HAL/HAX/SAM/OPR compatibility paths.  STO-004 later owns
refined REL-source union/order/capacity without adding modes to HCL.
