# STO-004 Contract: Balanced Refined Support Union And Prefix Planning

## Responsibility

STO-004 plans the maximal dense refined primary prefix whose unique union of
REL-001 source leaf IDs fits explicit caller capacity.  It defines support
union/order/capacity only.  It defines no contact/balance/relation meaning,
global relation cache, geometry, source-slot mapping, physical transform,
restriction/prolongation phase/weights/values, scratch reach, payload transfer,
backend, or scheduling.

## Stable Operations

```text
plan_balanced_refined_support_prefix(
    first_primary_id,
    leaf_count,
    source_counts,
    source_leaf_ids,
    selected_leaf_ids,
) -> (primary_count, selected_count)

maximum_balanced_refined_support_slots(
    first_primary_id,
    leaf_count,
    source_counts,
    source_leaf_ids,
) -> slot_count
```

`first_primary_id` and `leaf_count` accept Python/NumPy integer scalars except
booleans and rank-zero arrays.  Both are nonnegative, signed-int64
representable, and `first_primary_id <= leaf_count`.

`selected_leaf_ids` is caller-owned writable native-endian C-contiguous
`int64[S]`; its length is explicit selected capacity.  Let

```text
C = min(S, leaf_count - first_primary_id).
```

For the planner, `source_counts` is borrowed read-only C-contiguous
`uint8[C,D]` and `source_leaf_ids` is borrowed read-only native-endian
C-contiguous `int64[C,D,4]`.  Row `r` is the unchanged REL-001 source record for
canonical candidate leaf `first_primary_id+r`.  `D` may be zero or any
REL-001-valid subset, repetition, or reordering of noncenter directions; row
order defines support discovery.  Kinds, masks, and directions are deliberately
not inputs.  A complete traversal and its global progress maximum use one fixed
direction matrix/order across every window; changing it between windows defines
a different caller support policy.

For the maximum helper, the same representations may contain any bounded
candidate row count `C <= leaf_count-first_primary_id`; maxima over a complete
nonoverlapping partition of rows give the exact global progress capacity.

REL provenance is an upstream semantic precondition.  STO-004 validates the
plain representation required for safe independent use: every count is in
`[0,4]`, every active source ID is in `[0,leaf_count)`, and every trailing source
slot is exact `-1`.

## Candidate Window Sufficiency

The planner requires exactly `C=min(S,remaining)` rows.  This proves global
maximality:

- if a candidate rejects, the first rejection is represented in the window;
- if all `S` rows are accepted, `S` distinct primary IDs alone fill capacity;
- if fewer than `S` rows remain, accepting all reaches stream end.

A shorter arbitrary window could stop while another primary still fits and is
therefore rejected as an incomplete planner input.

## Exact Support Plan

Consider candidates in dense PRI-001 order.  Accepted primaries occupy

```text
selected_leaf_ids[:primary_count]
    = first_primary_id ... first_primary_id+primary_count-1.
```

Closure-only support follows.  For each candidate row, form a trial:

1. remove the candidate from support if previously discovered, preserving all
   other support order;
2. append it to the primary prefix;
3. scan directions `d=0..D-1`, then active source columns
   `q in [0,source_counts[row,d])`, appending each global leaf ID not already
   primary/support;
4. accept exactly when the unique union fits capacity.

This order preserves caller direction order and REL's canonical finer-source
order.  PHYSICAL records contribute zero sources; SAME/COARSER one; FINER one,
two, or four; mixed physical records contribute REL's neutralized sources.
Closure is nonrecursive.

If the first trial does not fit, raise
`ValueError("selected capacity cannot fit the first refined support closure")`
before mutation.  A later nonfit ends the chunk normally.  Success returns a
maximal dense primary prefix, unique selected IDs, stable support order, and a
bitwise-preserved suffix after `selected_count`.  Advancing by `primary_count`
covers every leaf exactly once as primary; support may recur and is not consumer
work unless promoted.

At end, exact zero candidate rows are required; return `(0,0)` without mutation
for every capacity.  Before end, zero capacity raises `ValueError` after input
representation validation and before policy execution.

## Maximum And Progress

For candidate row `r`, define the unique one-primary closure

```text
{first_primary_id+r} union {all active REL source IDs in row r}.
```

`maximum_balanced_refined_support_slots(...)` returns the largest such
cardinality in its bounded rows, or zero for no rows.  The maximum across a
complete partition is the exact topology/direction-specific capacity that
guarantees progress everywhere.

For canonical all-26 balanced nonperiodic Cartesian 3D relations, at most 56
distinct finer sources surround one primary (24 face, 24 edge, eight corner),
so 57 selected slots universally guarantee progress.  This bound is achieved;
a particular forest may require less.  WENO's exact maximum is 53.

## Validation, Errors, And Atomicity

Validation order is `first_primary_id` scalar kind/nonnegative/int64, then
`leaf_count` scalar kind/nonnegative/int64, counts representation, source
representation/paired shape, and selected output representation/writability.
Then validate cross-range `first_primary_id<=leaf_count`, exact candidate-window
shape, all output/input overlap, and a complete count/active-ID/trailing-sentinel
scan.  Unfinished zero capacity is checked after this scan.  The maximum helper
omits output/window-equality checks but validates its bounded cross-range and all
relation values.

Wrong scalar/array kinds or dtypes raise `TypeError`.  Invalid rank/layout/
writability/range/window/overlap/relation values/capacity raise `ValueError`.
Scalar overflow raises `OverflowError`.  Every ordinary failure and first-fit
error preserves the complete selected output.  Inputs and pointers are never
mutated or retained.

## Independent Evidence

The independent reference uses Python primary/support lists and scans rows in
the contracted order.  Evidence covers physical/same/coarser/finer and mixed
records; duplicates; future-primary promotion; window sufficiency and short
window rejection; first/later nonfit; suffix/end; exactly-once traversal;
bounded/global maxima; achieved 57 and face-only 25 limits; randomized balanced
REL composition; current-supported record equality; explicit mixed-record
source retention and direction-subset divergence; canonical all-26 union
equality where mixed sources duplicate reduced rows; WENO maximum53; read-only
inputs; every shape/count/source/sentinel/output error; and absence of geometry/
transfer/payload behavior.

## Performance And Memory

The pure planner uses linear membership in the caller selected prefix and no
hash, bitmap, global marker, or size-dependent scratch.  Its direct input is
`33*C*D` bytes of counts/sources plus `8*S` selected IDs.  A complete REL window
retained for immediate transfer is `35*C*D` bytes; with canonical 26 directions
and `C=S`, this is `910*S` bytes plus selected IDs.

These relation-window bytes are additional to WSP-001's canonical payload plus
single-ID-vector formula and must be included by a bounded refined executor.
The executor may reuse `selected_leaf_ids[:C]` as the dense REL candidate-ID
input before STO-004 overwrites the selected plan, yielding exact metadata
`35*C*D + 8*S` bytes.  If candidate and selected ID vectors coexist, add another
`8*C` bytes.

Measure planner/source scan/insert throughput, chunks, amplification,
utilization, fixed allocation, maximum-helper throughput, output/window bytes,
REL row generation, naive versus sliding row amplification, compaction/refill
bytes, and selected STO-001/003 gather.  Exact plans are hard gates.

## Immediate Composition

PRI-001 supplies dense candidate IDs, REL-001 supplies bounded source rows, and
STO-001/003 gathers all selected interiors.  A sliding executor may retain
unaccepted REL rows so each leaf relation is generated once; this is an
execution strategy over the stable arrays.  Later transfer planning consumes
accepted kinds/masks/sources and selected IDs while independently owning slot
mapping, access reach, phases, weights, order, scratch, and values.
