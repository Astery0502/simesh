# MOR-001 Contract: Cartesian 3D Level-1 Morton Mapping

## Responsibility

MOR-001 assigns every coordinate in a positive Cartesian 3D level-1 root grid
an exact zero-based dense Morton rank and produces the inverse coordinate map.
It defines no nodes, neighbors, boundaries, geometry, refinement, or forest
state.

## Exact Order

For a nonnegative integer `a`, define the mathematical bit spread

```text
spread(a) = sum(((a >> b) & 1) << (3*b), b >= 0).
```

The ordinary 3D Morton key is

```text
code(x, y, z) = spread(x) | (spread(y) << 1) | (spread(z) << 2).
```

The dense rank of an in-box coordinate `c` is the count of in-box coordinates
whose mathematical key is smaller than `code(c)`. Thus x, y, and z occupy bit
positions `3b`, `3b+1`, and `3b+2`; out-of-box coordinates are filtered and all
rank gaps are closed. For an equal-sided power-of-two cube, dense rank equals
the raw key. No raw key or key-width limit is part of the runtime interface.

## Inputs And Outputs

The stable compiled operation is

```text
fill_level1_morton(root_shape, coord_to_rank, rank_to_coord) -> None
```

- `root_shape` is borrowed read-only native-endian C-contiguous signed
  `int64[3]`, ordered `(nx, ny, nz)`, with every extent positive.
- `N = nx * ny * nz` is evaluated in Python integer arithmetic and must fit
  signed `int64`.
- `coord_to_rank` is caller-owned writable native-endian C-contiguous `int64`
  with exact shape `(nx, ny, nz)`.
- `rank_to_coord` is caller-owned writable native-endian C-contiguous `int64`
  with exact shape `(N, 3)`.
- The input and two outputs may not overlap. Validation completes before the
  unchecked kernel, so an invalid call mutates neither output.
- On success every output element is defined, inputs are unchanged, and no
  output or pointer is retained.

`level1_morton(root_shape)` is an allocating orchestration helper that returns
new forward and inverse arrays and delegates their fill to the stable operation.
Allocation failure is reported normally by NumPy.

## Exactness And Invariants

All values are discrete and exact; no tolerance applies.

- `coord_to_rank` is a permutation of `0..N-1`.
- `rank_to_coord` contains every in-box coordinate exactly once.
- `coord_to_rank[tuple(rank_to_coord[r])] == r` for every rank.
- `rank_to_coord[coord_to_rank[x,y,z]] == (x,y,z)` for every coordinate.
- Mathematical Morton keys along `rank_to_coord` are strictly increasing.

Type/dtype errors raise `TypeError`. Wrong shapes, nonpositive extents,
non-C-contiguity, read-only outputs, or overlap raise `ValueError`. An
unrepresentable volume raises `OverflowError`. No silent conversion, repair, or
payload-sized scratch is permitted.

## Performance And Memory

The compiled traversal is proportional to valid coordinates plus occupied
Morton prefixes. It uses the two required output arrays (`32*N` bytes total)
and `O(log(max(root_shape)))` C stack, with no heap scratch or per-coordinate
allocation. Parallel scaling is not relevant to this one-time dependency-order
mapping unless later composed measurements make construction material.

## Immediate Composition

For M0, Morton rank is the zero-based global level-1 block ID. This does not
make an arbitrary FND-001 chunk slot equal to the block ID. TOP-001 consumes
`rank_to_coord` to identify a block coordinate and `coord_to_rank` to resolve an
in-domain neighboring coordinate; TOP-001 owns boundary classes and sentinels.
