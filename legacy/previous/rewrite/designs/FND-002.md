# FND-002 Design: Access And Halo Requirements

## Problem

Storage and halo providers need to know which input cells a consumer may read
without knowing the consumer's formula. The current implementation often uses
a boolean `requires_ghosts`, which cannot express how many cells are needed or
whether the lower and upper sides differ.

## Choices Considered

A symmetric radius is simple but overfetches for forward, backward, and other
asymmetric kernels. Explicit offset lists describe sparse stencils exactly, but
valid payload regions are rectangular and provisioning only needs the smallest
axis-aligned bound. Inferring the access kind from reach would make pointwise
operators indistinguishable from streaming reductions. Callback or descriptor
class hierarchies would prematurely define an executor.

## Selected Direction

Use three named access kinds: pointwise, fixed local stencil, and streaming
reduction. Associate each input with nonnegative lower- and upper-reach triplets
in `(x, y, z)` order. The reach is the tight axis-aligned bound over every cell
the consumer may read; a stencil may remain sparse inside that box.

Provide exact region expansion, contraction, and support checks. Empty boxes
are canonicalized explicitly so a no-output request never creates a false input
requirement. Keep field selection, formulas, exact offsets, reduction state,
halo filling, storage protocols, and scheduling in their later capabilities.
